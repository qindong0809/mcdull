# 架构分层与依赖治理规范

> 目的：防止易变业务细节沉淀到稳定层，导致局部变更触发全项目重编译。

---

## 一、向 framework 加东西前，先问三问

任何类/字段/枚举在准备放进 `mcdull-framework*` 之前，必须逐条回答：

1. **改不改？** 是否真的必须改 framework？能否放在业务模块内解决？
2. **为什么？** 它是否是被所有模块共用的技术契约，而非某个业务的细节？
3. **是否会随业务改动？** 新增成员时，是改一行业务配置，还是改框架源码让所有人重编译？

---

## 二、分层职责一句话

| 层 | 放什么 | 禁止 |
|---|---|---|
| `mcdull-framework*` | 与业务无关的技术契约、基础模型、横切能力 | 依赖 business |
| `mcdull-framework-base` | 最小公约数：标记接口、Result、异常、通用模型 | 任何业务语义 |
| `mcdull-business-common` | 跨业务复用的业务能力（审计/文档/文件） | 依赖任何 facade/impl |
| `mcdull-business/{module}` | 具体业务，facade/impl/bootstrap 三段式 | 依赖其他业务 impl |
| `mcdull-devtools` | 研发/运维工具（运行时用不到） | 被业务依赖 |

---

## 三、判定规则

- **稳定结构**（形状不变，如接口、Result）→ 可进 framework。
- **易变值集合**（枚举、字典、业务字段）→ 留业务侧，framework 只定义轻量接口。
- **零引用代码** → 先删除，不沉淀。
- **只有单个业务用** → 放该业务模块，不进公共层。

口诀：**框架可以有"形状"，不能有"取值表"。**

---

## 四、公共层解耦模式（实战决策）

当 common 的工具类需要业务模型（如 facade 中的 BO）时，**禁止让 common 依赖 facade**。按模型的稳定性选择解耦方式：

| 模型性质 | 例子 | 解耦方式 | 落点 |
|---|---|---|---|
| **稳定结构契约**（形状固定，出现在 facade 契约签名里，有读写操作） | `IAreaVO`（4 个固定方法） | **上移**到 framework-base | base 加一个轻量接口，facade 原接口保留为兼容壳 `extends` 它 |
| **易变业务模型**（字段会增减，只在工具内部用，只读） | `DynamicFieldBO` | **轻量接口解耦** | base 定义最小接口（`getName`/`getDropdownList`/`isSelectable`），业务模型 implements 它；工具只认接口 |

要点：
- **稳定结构可上移 base**——一个接口不会让 base 变重；它会随业务改动吗？不会。
- **易变模型只抽最小行为接口**——不把整个 BO 或枚举搬上 base；枚举判断（`isSelectable`）留在业务模型内部，保住类型安全。
- **工具类参数用 `? extends` 协变**——如 `Map<String, ? extends List<? extends ExcelField>>`，调用方无需改代码。

案例结论：`common → system-facade` 反向依赖已用上述两法消除，common 源码与 pom 均零 facade 依赖。

## 五、反模式清单

| 反模式 | 案例 | 正确做法 |
|---|---|---|
| 值集合下沉框架 | 计划下沉 `FormItemControlTypeEnum`、`DynamicFieldBO` | 否决；用第四节轻量接口解耦 |
| 公共层依赖上层 | `business-common` 依赖 `system-facade` | 已修复：结构上移 base + 轻量接口解耦（非删除业务类） |
| 工具认识业务枚举 | `ExcelTemplateUtil` 判断 `== SELECT` | 判断收进业务模型的 `isSelectable()`，工具只调布尔方法 |
| 凭不可靠统计删代码 | 误判 `ExcelTemplateUtil`/`AreaFillUtil`/`UserRefUtil` 为 0 引用 | 用 PowerShell `Select-String` 复核；证据反直觉必交叉验证 |
| 死代码沉淀 | `recommend/`、`engine/`、`word/`、`CsvUtil` | 可靠统计确认 0 引用后再删 |

**铁律：诊断未闭环，不动手术；证据反直觉，必先复核。**

## 六、硬性约束

- ArchUnit：Controller/Service/Manager/Mapper 分层、facade 不依赖 provider、禁标准输出、禁泛型异常（5 个业务模块均有架构测试）。
- Mapper 包路径统一 `..web.mapper..`；包路径 0 命中不等于通过，而是守护失效。
- 新增业务模块必须建 `XxxArchitectureTest`（复制 `SystemArchitectureTest`）。
- 依赖方向：`framework ← business-common ← business`，禁止反向。

---

## 七、模型表示边界约定

> 目的：防止「一个概念 N 个类」失控。判断标准不是"类是否重复"，而是**它出现在哪个边界**。

| 表示 | 命名 | 归属包 | 允许出现的位置 | 职责 |
|---|---|---|---|---|
| 持久化实体 | `*Entity` | `..model.entity..` | 仅 Mapper ↔ Service | 与表结构一一对应，禁止出现在 Controller 签名与 facade 契约 |
| 契约 DTO | `*DTO` | `..facade.model.dto..` / `..model.dto..` | 跨服务 RPC 入/出参 | 服务间传输，**不绑定任何展示格式注解** |
| 视图 VO | `*VO` | `..model.vo..` | 仅 Controller 出参 | 携带展示关注点（时区、日期格式、菜单树结构） |
| 命令 DTO | `*AddDTO` / `*UpdateDTO` / `*QueryDTO` | `..model.dto..` | 仅 Controller 入参 | 按操作分化校验规则，是合法的多态而非冗余 |
| 业务/会话 BO | `*BO` / `*SessionBO` | `..model.bo..` | Service / Manager 内部 | 承载不属于实体的视角字段（如 ip、userAgent、userType） |

**禁止的方向：**

1. `*Entity` 出现在 Controller 公共方法签名或 facade 契约签名中（防止表结构泄漏与敏感字段外传）。
2. facade 契约包引用 impl 包中的任何类（已有 ArchUnit 规则守护）。
3. `*VO` 继承 `*Entity`（已有 ArchUnit 角色规则守护）。

**已知例外（不必急着消除，但要有意识）：**

- `UserVO extends UserDTO`：契约 DTO 的字段被视图层复用，仅为追加两个带 `@DynamicDateFormat` 的日期字段。这是**字段复用**而非"第五种表示"，但存在同名字段遮蔽的隐患——通过 `UserVO` 引用赋值走子类字段、通过 `UserDTO` 引用赋值走父类字段，二者不互通。新增同类视图对象时避免此写法，优先显式组合。
